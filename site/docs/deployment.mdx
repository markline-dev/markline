## Static hosting

```bash
markline export   # → ./out
```

Upload `out/` to any static host — a CDN, GitHub Pages, Netlify, or S3.

<Tabs>
  <Tab title="GitHub Pages">
    The scaffolded `.github/workflows/deploy.yml` exports and deploys on push to
    `main`, building under `/<repo>` for project sites.
  </Tab>
  <Tab title="Netlify">
    `netlify.toml` sets the build command to `npx markline export` and publishes `out`.
  </Tab>
</Tabs>

<Note>On static hosts the API playground runs in direct-fetch mode. Set
`api.playground.proxy` to `"never"`.</Note>

## Node server

```bash
markline build && markline start
```

It serves pages from the last build, so rebuild to update or remove them. A page
added since then is rendered on each request until you do.

This enables the playground's server-side proxy for APIs without CORS. The
scaffolded `Dockerfile` builds and serves the site:

```bash
docker build -t my-docs . && docker run -p 3000:3000 my-docs
```

## Sub-path hosting

Serving under a path prefix (e.g. a GitHub Pages project site)? Set the base path
so assets and search resolve correctly:

```bash
MARKLINE_BASE_PATH=/my-repo markline export
```

## What a build can run

Building a Markline site runs its code. MDX pages can run JavaScript at build time,
as `npm install` or any other build tool can, so only build repositories you trust.

That includes preview deploys of pull requests from people outside your team. Don't
build those automatically with access to secrets.

Serving a built site is different. Pages are rendered from your site's own files,
never from what a reader sends, so a reader can't run code on your server through
them.
